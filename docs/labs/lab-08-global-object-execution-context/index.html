The Global Object & Global Execution Context

Every JS program starts with one context that's created before anything else. Lab 05 showed it sits at the bottom of the call stack — this lab shows what it actually contains, and where your top-level declarations really end up.

Mental Models

Mental Model 1 of 5Always at the Bottom, Never Popped

Every other context (Lab 05) gets pushed and eventually popped. The global context is the one exception — it's built first, before anything else, and stays until the whole program ends.

Mental Model 2 of 5var/function Attach to a Real Object

A top-level var or function declaration doesn't just exist abstractly — it becomes an actual property on a real, inspectable object: globalThis.

Mental Model 3 of 5let/const Get a Private Home Instead

let/const are still registered during the global context's creation phase (Lab 06) — they just don't attach to globalThis the way var and functions do.

Mental Model 4 of 5An Analogy: Lobby Directory vs Private Office

A var at the top level is like a business listed on the building's public lobby directory — anyone in the building can look it up by name. A let/const is like a private office with no public listing — it's still a real place, just not something you can find by browsing the directory.

Mental Model 5 of 5Misconception: "Global Object" ≠ "Global Scope"

"Global scope" is the abstract idea of "every name reachable from the top level." globalThis is one specific, concrete object — only some of the names in global scope (the vars and function declarations) actually live on it.

The Concept

The global execution context is the foundation everything else sits on

Lab 05 introduced the call stack and mentioned the global context gets pushed first, before any of your code runs. This lab looks at what actually makes that first context special. Unlike every function-call context — created on demand, popped when the call returns — the global context is built exactly once, right at the start, and is never popped for as long as the program keeps running.

Why does a global object exist at all?

In JavaScript's earliest use as a browser scripting language, the engine needed some way to expose built-in browser features — things like alert, document, or setTimeout — as ordinary values a script could just use by name, with no import step required. The solution was to put them all as properties on one shared object. Once that object existed, it made sense to plug top-level var declarations and function declarations into the exact same object too, so your own top-level code and the browser's built-in features lived in one unified, lookup-by-name place.

var/function attach; let/const don't

Building directly on Lab 06's creation phase and Lab 07's TDZ model: during the global context's creation phase, every top-level var and function declaration is registered and attached as a property of the global object. Every top-level let/const is registered too — starting in the Temporal Dead Zone, exactly like inside any other block — but it's kept in a separate, private record that globalThis has no access to at all.

Cross-language note

Common concept: a place top-level names live.

Python: each module has its own namespace object, but there's no single shared object across every file the way globalThis is shared across every classic script on one page.

JavaScript: this whole "attach to a shared object" behavior is actually specific to classic, non-module scripts. A modern JS module (Lab 47 covers this) gets its own private top-level scope — nothing it declares attaches to globalThis at all, var included. Node.js goes even further: every file is automatically wrapped so top-level var doesn't leak onto the shared global object either.

Reflection Questions

Write your own answer first — the blurred text is one possible answer, not the only correct one.

Reflection 1 of 3. Before this lab, did you assume "global variable" and "property on the global object" were just two names for the same thing? How does that assumption break for let/const?

It's a very natural assumption, since for var they genuinely are the same thing. The break happens with let/const: they're fully "global" in the sense of being reachable from anywhere at the top level, but they never show up as a property on globalThis — proving "global variable" and "property of the global object" are related but not identical ideas.

Reflection 2 of 3. Why might the designers of let/const have deliberately chosen to stop attaching to the global object, given how useful that attachment sounds?

The same attachment that sounds useful is exactly what causes the silent collisions this lab demonstrated — two unrelated pieces of code sharing one object by accident. Once block scope existed as an alternative, keeping top-level names off a giant shared object removed an entire category of naming-collision bugs, at the cost of losing the "discoverable directory" convenience.

Reflection 3 of 3. Predict: if you assign to a completely undeclared name without var/let/const at all (e.g. just brandNewName = "hi";) in non-strict mode, based on today's model, where do you think that name ends up?

It ends up exactly where globalThis.brandNewName = "hi" would put it — as a new property on the global object — because in non-strict mode, assigning to an undeclared name is treated as an implicit global assignment rather than an error. This is widely considered a design mistake in the language, and is exactly the kind of accident let/const's stricter rules (Lab 07) help prevent.

What Breaks If This Understanding Is Wrong?

If you don't know top-level vars share one real object across every classic script on a page, a mysteriously overwritten variable from a completely unrelated file will look like a bizarre bug instead of a predictable naming collision — and you'll waste time looking in the wrong file entirely.

What JavaScript Concept Was Learned Today?

The global execution context is permanent and created first, and top-level var and function declarations attach as real properties on globalThis — while let/const stay off it entirely, even though both are equally "global."
