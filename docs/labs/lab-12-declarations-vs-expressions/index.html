Functions Lab 12

Function Declarations vs Function Expressions

Two ways of writing a function look almost identical on the page, but the engine sets them up at completely different moments. This lab is where Lab 06's creation phase meets Lab 11's idea that a function is a value.

What this lab produces: no files, no commit — a pure concept lab. You'll run short snippets in a console or with node.
Concept type: Common Concept, JavaScript-Specific Rules
ƒ
FUNCTIONS & ABSTRACTION 4 of 10

Every language needs a way to define reusable computation. JavaScript gives you two syntaxes for it — one the engine sets up before any code runs, one it treats as an ordinary value to be assigned.

Mental Models

Mental Model 1 of 5Declaration: Set Up Early

A function declaration (a statement that starts with the word function and a name) is processed during the creation phase from Lab 06. By the time the first line runs, the name already points at a complete, callable function.

Mental Model 2 of 5Expression: A Value You Assign

When function shows up somewhere a value could go — right of an =, as an argument, inside parentheses — it's an expression. It creates a function object at the moment that line runs, and something else (like a variable) has to hold on to it.

Mental Model 3 of 5The Variable Exists Early; Its Value Doesn't

With var, the name expressed is created in the creation phase and set to undefined. The function only gets in once the assignment line actually executes — so calling it earlier means trying to call undefined.

Mental Model 4 of 5An Analogy: Directory vs. Note

A declaration is like an entry already printed in the building directory before anyone arrives: from the first minute you can look it up. An expression is a note someone hands you partway through the day — before that moment, there's nothing to look up.

Mental Model 5 of 5Misconception: "The Name After function Is a Normal Variable"

In var f = function g() {}, the name g is not added to the surrounding scope. It exists only inside the function's own body (handy for recursion and clearer stack traces). Outside, only f works.

Learning Objectives

  1. Objective 1 of 4 — I can look at a function definition and say whether it's a declaration or an expression, using the "does the statement start with function?" test.
  2. Objective 2 of 4 — I can predict whether a call placed above a function's definition will work, fail with TypeError, or fail with ReferenceError.
  3. Objective 3 of 4 — I can explain why calling a var-assigned function early gives TypeError while a const-assigned one gives ReferenceError.
  4. Objective 4 of 4 — I can state where a named function expression's name is, and isn't, visible.

The Concept

Two ways to write what looks like the same function

Here are two definitions that behave the same once everything is running: 

function greet() { return "hi"; }          // declaration

var greet2 = function () { return "hi"; };  // expression

A function declaration is a statement — a complete instruction in its own right — that begins with the word function followed by a name. A function expression is the same function ... text used where a value is expected: on the right of an =, as an argument to another call, or wrapped in parentheses. (An expression is any piece of code that produces a value; Lab 11 showed that a function is such a value.)

A reliable test: if the statement begins with the word function, it's a declaration; if function shows up anywhere else, it's an expression.

Declarations are processed in the creation phase

Lab 06 showed that before a scope's code runs line by line, the engine makes a creation phase pass that registers its names. For a function declaration, that pass does something special: it registers the name and builds the finished function object right then. Nothing about the function is left to do later. 

console.log(add(2, 3));   // 5 -- works, even though add is defined below

function add(a, b) {
  return a + b;
}

This is called hoisting of the whole function: it behaves as if the definition were moved to the top of its scope. It's why many people put the main logic of a file first and the helper declarations below it.

Expressions follow the rules of whatever variable holds them

A function expression creates its function object only when execution reaches that line. Until then, whether the name is usable depends entirely on how the variable was declared — the rules from Lab 06 and Lab 07, unchanged:

  • var: the name exists from the start with the value undefined. Calling it early means calling undefined, which raises TypeError: x is not a function.
  • let / const: the name exists but is locked in the temporal dead zone until its declaration line runs. Touching it early raises ReferenceError: Cannot access 'x' before initialization.

Same situation — "I called a function before its line" — two different error types, and the type tells you which kind of declaration you're dealing with. (Exact wording of the messages varies slightly between engines; the error types don't.)

Names: anonymous, named, and inferred

A function expression may leave out its name (an anonymous function expression) or include one (a named function expression): 

var a = function () {};              // anonymous expression
var b = function inner() {};         // named expression

console.log(a.name);   // "a"     -- inferred from the variable it was assigned to
console.log(b.name);   // "inner"

Two details worth knowing. First, when an anonymous function expression is assigned straight to a variable, modern engines infer its name property from that variable (Lab 11's name again). Second, the inner name of a named expression — inner above — is visible only inside that function's own body, never in the surrounding scope. That makes it useful for a function that needs to call itself, and gives clearer names in error stack traces.

Cross-language note

Common concept: defining a named, reusable unit of computation.

Python: def is an ordinary statement that runs when reached — calling the function on an earlier line raises NameError. There is no hoisting of def. lambda is Python's expression form, limited to a single expression.

JavaScript: declarations are set up early (callable above their definition); expressions are values created when their line runs, with no single-expression limit.

Which should you use?

Neither is "correct." A reasonable rule of thumb: use a declaration for a named helper that you want available throughout its scope, and a function expression when the function is itself a value you are passing, returning, or storing — for example const handler = function () { ... }; or an argument to another function (Lab 16). Whichever you choose, now you know exactly what the engine does with it.

Two cautions. Function declarations written inside if blocks or loops have a historically inconsistent behavior across engines — recognize them in old code, but avoid writing them; use a const and an expression there. And arrow functions (Lab 20) are a third, shorter expression syntax: they follow the expression rules from this lab.

Reflection Questions

Write your own answer first — the blurred text is one possible answer, not the only correct one.

Reflection 1 of 3. In your own words, why does declared() work above its definition while expressed() doesn't, even though both end up as functions?

A declaration is handled in the creation phase, which builds the full function before any line runs. An expression is only evaluated when execution reaches its line, so until then the variable that will hold it is just undefined (or locked, for let/const).

Reflection 2 of 3. If you've used Python, compare calling a function above its def with calling a JavaScript declaration above its definition. What does each tell you about when the function comes into existence?

In Python, def is an ordinary statement that executes when reached, so the function doesn't exist before it and an early call fails with NameError. In JavaScript a declaration is set up before the scope's first line runs, so it exists "from the start." The same word (define a function) means two different moments in time.

Reflection 3 of 3. Is relying on function-declaration hoisting a helpful feature or a hazard? Argue one side using what this lab showed.

Helpful: you can put the main story of a file at the top and helpers below. Hazardous: a reader may not realize code is calling something defined far below, and if a helper is later converted to an expression (say, const helper = ...), calls above it silently turn into ReferenceErrors. A consistent style (always define before use, or always declare) avoids the surprise.

What Breaks If This Understanding Is Wrong?

If declarations and expressions feel interchangeable, Lab 13 (IIFEs) won't make sense — the extra parentheses exist purely to force the parser to treat function as an expression. You'll also misdiagnose "is not a function" and "before initialization" errors, which point to the two different failure paths covered here, and callbacks (Lab 16) won't make sense, since a callback is typically a function expression handed over as an argument.

What JavaScript Concept Was Learned Today?

JavaScript has two function syntaxes with different timing: a declaration is fully set up in the creation phase and callable anywhere in its scope, while an expression is a value created when its line runs and follows the hoisting rules of the variable that holds it. A named expression's own name is visible only inside itself.

Relates to: ƒ Functions & Abstraction (4 of 10) — how do we package computation? JavaScript offers two packaging syntaxes, set up at two different moments.
