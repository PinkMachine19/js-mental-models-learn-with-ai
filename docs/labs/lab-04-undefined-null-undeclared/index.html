The Concept

"Absence of a value" is common; JavaScript's three-way split isn't

Most languages have some way to represent "no value" — but JavaScript is unusual in having three genuinely different situations that all sound like "nothing" in casual conversation. Telling them apart precisely is the actual skill this lab teaches.

Cross-language note

Common concept: representing "no value."

Python: has one deliberate "nothing" value, None, and reading a name that was never assigned anywhere raises NameError — conceptually close to JavaScript's undeclared-identifier case below.

JavaScript: splits this into two separate concepts — the engine's own default empty state (undefined) and your own deliberate empty state (null) — on top of the undeclared-identifier case Python already has an equivalent for.

The three cases

  1. undefined — a variable exists and was declared, but was never assigned a value. This is the engine's own default, not something you typically write yourself.
  2. null — a variable exists, and you deliberately assigned it the value null to mean "no value belongs here right now." It's a real primitive type (Lab 03), and you always assign it on purpose.
  3. Undeclared identifier — the name was never declared anywhere the engine's scope-chain search (Lab 09) can find. Reading it throws a ReferenceError instead of returning any kind of empty value.

Reflection Questions

Write your own answer first — the blurred text is one possible answer, not the only correct one.

1. When would you deliberately assign null to something instead of just leaving it undefined?

When "no value yet" is a meaningful state your own code chose, versus a variable that simply hasn't been touched. For example, a selectedSeat field that starts as null communicates "the user hasn't picked one," which reads differently from a variable that was just never assigned by accident.

2. Why might a language deliberately make typeof safe on undeclared names, when directly reading them throws?

It gives code a way to safely ask "does this even exist" without wrapping every check in a try/catch — useful for feature-detection style code checking whether some optional global exists before using it.

What Breaks If This Understanding Is Wrong?

Confusing "declared but empty" with "never declared" will make error messages feel random — you'll misread a real bug (a typo'd variable name causing a ReferenceError) as if it were just an empty value to work around, instead of fixing the actual typo.

What JavaScript Concept Was Learned Today?

The difference between the engine's own default empty value (undefined), your own deliberate empty value (null), and a name that doesn't exist at all (undeclared, throws).
