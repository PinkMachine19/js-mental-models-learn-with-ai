IIFEs: Immediately Invoked Function Expressions

Create a function and call it in the very same breath, purely to get a private scope for a moment. Historically one of the most common patterns in JavaScript — and still everywhere in older code.

What this lab produces: no files, no commit — a pure concept lab. You'll run short snippets in a console or with node.
Concept type: Mostly JavaScript-Specific
ƒ
FUNCTIONS & ABSTRACTION 4 of 10

Every language needs a way to keep temporary names from spilling into the rest of the program. JavaScript's older answer was to borrow a function's scope — the IIFE — and it only makes sense once you've seen Lab 12's expressions.

Mental Models

Mental Model 1 of 5Create It, Call It, Done

An IIFE is a function expression (Lab 12) wrapped so that it's called the instant it's created: (function () { ... })();. There's no name to call it by again; it runs once and its purpose is finished.

Mental Model 2 of 5A Private Scope for Throwaway Names

Variables declared with var inside the function belong to that function's scope (Lab 09), so they can't be seen from outside. The IIFE's whole job is to use that wall: do some work, leave nothing behind.

Mental Model 3 of 5Parentheses Change How the Parser Reads It

A statement that starts with the word function is parsed as a declaration, which needs a name and can't be called on the spot. Wrapping the whole thing in parentheses puts it in expression position (Lab 12), where it can be called.

Mental Model 4 of 5An Analogy: A Disposable Workbench

Set up a bench, do the messy work with sawdust and scraps, carry out only the finished piece, and discard the bench. Anyone looking at the shop afterward sees the product and none of the mess. An IIFE hands back (at most) a result and leaves its temporaries behind.

Mental Model 5 of 5Misconception: "A Block Is Enough to Contain a var"

Lab 07: var is scoped to the whole function, not to blocks like { }, if or for. That is precisely why people reached for a function — the only thing that contained var — and wrapped it into an IIFE.

The Concept

The problem: var leaks, and files used to share one global scope

Lab 07 showed that var ignores blocks: a loop counter or temporary declared with var inside for { } is still visible after the loop. Lab 08 added that, in a browser <script>, top-level var declarations became properties of the global object — shared with every other script on the page. Two scripts that both declared var i or var config at top level could silently overwrite each other.

Before let/const (ES2015) and modules (Lab 47), there was exactly one construct that created a new place for var names to live and then disappear: a function. The IIFE is that idea, made routine.

Anatomy of an IIFE

(function () {
  var temp = "private";
  console.log(temp);
})();

IIFE stands for Immediately Invoked Function Expression: a function expression (Lab 12) that is invoked (called) immediately. Three pieces:

  1. function () { ... } — an anonymous function expression. Nothing has run yet.
  2. The surrounding ( ... ) — parentheses that make the parser read it as an expression.
  3. The final () — the call operator (Lab 11) that runs the function right now.

The function is created, called once, its scope is used, and then it's garbage — no variable ever pointed at it.

Why those parentheses aren't optional

If a statement begins with the word function, the parser reads it as a declaration (Lab 12). A declaration requires a name, and a declaration is a statement, not a value, so it can't be followed by (). This line is a syntax error: 

function () { console.log("x"); }();   // SyntaxError: Function statements require a function name

Wrapping in parentheses makes the first token the (, so the parser is in expression position. Other tricks that achieve the same thing by putting anything in front of function are !function () { ... }(); and void function () { ... }();. Another accepted layout moves the call inside: (function () { ... }());. They all work for the same reason. The parenthesized form is by far the most common.

Passing values in, returning values out

An IIFE is still a function, so it can take arguments and return a value. The arguments go in the final parentheses and the return value is whatever the whole expression evaluates to: 

var result = (function (limit) {
  var last;
  for (var i = 0; i < limit; i++) { last = i * 2; }
  return last;
})(3);

console.log(result);    // 4
console.log(typeof i);  // "undefined" -- i never escaped

Returning a function from an IIFE gives you a function that can still use the IIFE's private variables after the IIFE is long finished — e.g. var nextId = (function () { var n = 0; return function () { return ++n; }; })();. How that's even possible is the topic of Lab 14 (closures); for now, just notice that n is reachable only through nextId.

Cross-language note

Common concept: keeping temporary names from leaking into shared scope.

Python: every file is already its own module namespace, so this problem barely arises; a function body is the only extra scope you'd normally create.

JavaScript: classic scripts on one page share a single global scope, and var ignores blocks — so the IIFE was invented to fake the isolation Python gets for free.

Do you still need them? Mostly no — but you'll still read them

Two later features handle most of what IIFEs used to do:

  • let/const with blocks: { let temp = 1; } contains temp without any function (Lab 07).
  • ES modules (Lab 47): each file has its own scope, so top-level names aren't shared.

You will still meet IIFEs in three places: old code and libraries written before ES2015; bundler output, which often wraps each file in one; and the occasional modern use such as (async () => { ... })();, which gives top-level code an await-capable function to run in (arrow syntax is Lab 20; async is Lab 46). This lab is tagged historical-but-important for that reason: recognize it instantly, write it rarely.

Reflection Questions

Write your own answer first — the blurred text is one possible answer, not the only correct one.

Reflection 1 of 3. Before let/const existed, how would you have kept a helper variable from leaking into the whole page? What does that tell you about why IIFEs became so common?

The only thing that contained a var was a function, so people wrapped their code in a function and called it right away. Since this was needed in nearly every script, it became a standard idiom — a workaround for the missing block scope that later features finally supplied.

Reflection 2 of 3. In Python, a module's top-level names are already private to that file. What does this lab suggest was different about JavaScript's scripts, and why did that matter?

Classic browser scripts all shared a single global scope, so top-level vars from different files could collide. An IIFE gave each file its own private scope, doing manually what Python's per-file module gives automatically. ES modules (Lab 47) finally gave JavaScript the same default.

Reflection 3 of 3. Predict: var x = 1; (function () { var x = 2; })(); console.log(x); — what prints, and which earlier lab explains why?

It prints 1. The IIFE's var x is a separate variable in the IIFE's own scope that shadows the outer x only inside it. Lab 09's scope chain explains it: the final log runs in the outer scope, which never sees the inner binding.

What Breaks If This Understanding Is Wrong?

Without this lab, a huge amount of real-world JavaScript looks like syntax noise — libraries and bundler output start and end with (function () { and })();. You'd also miss why the parentheses are mandatory, and Lab 14 and Lab 15 (closures, factories, the module pattern) build directly on IIFEs as their first, simplest use.

What JavaScript Concept Was Learned Today?

An IIFE is a function expression that is called the moment it's created, used to get a throwaway private scope — historically the only way to contain var. The wrapping parentheses are what force the parser to treat function as an expression; modern block scope and modules replace most uses, but the pattern is everywhere in older code.
