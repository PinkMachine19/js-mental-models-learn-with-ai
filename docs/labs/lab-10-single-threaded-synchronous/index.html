A short but load-bearing lab: JavaScript can only ever do one thing at a time. Every lab since Lab 05 has quietly relied on this — now it becomes explicit.

Mental Models

Mental Model 1 of 5One Stack, One Active Thing, Always

There's no second call stack running somewhere else in parallel. Every lab so far has really been describing the only execution path JavaScript ever has.

Mental Model 2 of 5Synchronous = Fully Finish, Then Advance

Each line of code runs to completion before the engine even considers the next one — there's no partial overlap, no "starting the next line a little early."

Mental Model 3 of 5A Busy Loop Blocks Everything

Since there's only one thread, a synchronous block that takes a long time to run doesn't just delay other JavaScript — it delays timers, click handling, and page rendering too, all of which share that same single thread.

Mental Model 4 of 5An Analogy: One Cashier, One Register

A single cashier can only ever help one customer at a time, start to finish, no matter how long the line behind them gets. Every other customer simply waits their turn — nobody gets served "a little bit" in parallel.

Mental Model 5 of 5Misconception: "Async" ≠ a Second Thread

Seeing the word async in code can suggest something is now running in parallel. It isn't — JavaScript still has exactly one thread and one call stack. What "async" code actually does with that single thread is the subject of several labs much later in this curriculum.

Learning Objectives

  1. Objective 1 of 3 — I can state, precisely, what "single-threaded" and "synchronous" each mean, and explain that they're two related but distinct properties.
  2. Objective 2 of 3 — I can predict what happens to a scheduled timer callback while a long synchronous block is still running.
  3. Objective 3 of 3 — I can explain why the word async in JavaScript does not mean "runs on a separate thread."

The Concept

Two related but distinct words: single-threaded and synchronous

Single-threaded means there is exactly one thread — one literal sequence of instructions the CPU is following for your program — with no second thread running alongside it to pick up other work. Synchronous means each instruction fully completes before the next one begins; there's no partial overlap between one line and the next. JavaScript is both: because it's single-threaded, its normal execution has to be synchronous — with only one thread available, there's nothing else that could run concurrently with the current line anyway.

Every lab so far has already been describing this constraint

Lab 05's call stack only ever has one active context because there's only one thread to run it on. Lab 09's scope chain search happens as one uninterrupted operation, with no other code able to run partway through it. None of this was ever stated as a separate rule before now — it was the unspoken assumption underneath everything already covered.

What actually happens with something scheduled for "later"

If JavaScript can only run one thing at a time, what happens to something like a timer callback? It doesn't run early, and it doesn't interrupt whatever's currently executing — it waits until the single thread is completely free, meaning every currently-running synchronous line of code has fully finished, all the way back down to an empty call stack. Only then does the engine even consider starting something new. (The full mechanism behind exactly how that "something new" gets picked is the event loop, covered starting at Lab 41 — this lab is only about the constraint that makes an event loop necessary in the first place.)

Reflection Questions

Reflection 1 of 3. Before this lab, if someone had asked you "does JavaScript run things in parallel," what would you have said, and why?

Words like "async," "background," and "concurrently" are common enough in everyday descriptions of JavaScript that it's easy to assume some form of real parallelism is happening. This lab's point is that none of that vocabulary changes the underlying fact: exactly one thread, exactly one thing running at any instant.

Reflection 2 of 3. Have you ever seen a webpage freeze up completely during some heavy operation? Reframe that experience using this lab's model — what was actually happening on the single thread at that moment?

A frozen page during heavy JavaScript work is this lab's busy-loop experiment happening for real — some synchronous block of code occupied the single thread long enough that rendering, scrolling, and click handling all had to wait in line behind it, with no way to cut in.

Reflection 3 of 3. This lab said the full mechanism for "how something scheduled for later actually gets picked to run" is covered starting at Lab 41. Based only on what you know now, what's one specific question you'd want that later lab to answer?

A natural question: if two different callbacks both become eligible to run at the same moment — say, a timer and a network response arriving at the same time — which one actually gets to go first, and is that decision predictable or arbitrary? (It's predictable, and Lab 41 onward covers exactly how.)

What Breaks If This Understanding Is Wrong?

If you believe JavaScript can genuinely run two pieces of your own code at the same instant, the entire event-loop model later in this curriculum will look contradictory instead of logical — every explanation of task queues and microtasks assumes, as a starting fact, that only one thing can ever be actively running.

What JavaScript Concept Was Learned Today?

JavaScript is single-threaded and synchronous by default — exactly one thing runs at a time, and a scheduled callback can never interrupt code that's already running, no matter how short its requested delay.
