Execution Context & the Call Stack

One function calling another feels instant and simple. Underneath, the engine is managing a strict, orderly stack of paused work. That stack is what this lab makes visible.

Every language needs some model for how source code becomes running computation, step by step. This lab is JavaScript's answer.

Mental Models

One Active Tray at a Time

Only the top tray is being worked. Everything below it is real, held, and waiting — not forgotten, not running, just paused.

What One Tray Holds

Every call gets a record like this. The engine's name for a tray is an execution context.

Add on Call, Remove on Return

A tray only ever leaves the stack from the top, and only once that order is fully done — never before, never out of order.

The Concept

The call stack itself is not a JavaScript invention

Python, Java, C#, and most mainstream languages/runtimes track active function calls with a call stack too — it's a general programming-language mechanism, not something JavaScript came up with. What's specific to JavaScript is the exact shape of the record it keeps for each call — the execution context — and how that record is built. That's the actual subject of this lab.

Cross-language note

Common concept: call stack / stack frames.

Python: every Python call pushes a frame too — it's why a RecursionError exists, the same underlying idea tested in Question 3 above.

JavaScript: same idea, one call stack per thread — what's JavaScript-specific is what gets stored in each context, next.

What an execution context actually is

Whenever JavaScript runs any function — including the top-level code in a file — it first builds an execution context: a small record tracking that call's own variables, where to resume once it's done, and a link back to whoever called it (the second diagram above). Calling a function pushes a new context onto the call stack. Returning from it pops that same context back off.

What the engine is doing, step by step

  1. Before any of your code runs, it builds the global execution context and puts it on the stack first.
  2. Each function call builds a new context for that specific call and puts it on top of the stack.
  3. The engine only ever works on the context at the top — it does not return to whatever called it until that top context finishes.
  4. When a call finishes, its context comes off the top, and the caller picks up exactly where it left off.

What the engine effectively does:
1. global context on the stack
2. takeOrder() called -> its context pushed, logs "order taken"
3. brewCoffee() called -> its context pushed, logs "coffee brewed"
4. brewCoffee() finishes -> its context popped
5. back inside takeOrder(), logs "order handed to customer"
6. takeOrder() finishes -> its context popped

completely finished -- the engine never jumps back to a paused
context while something is still sitting on top of it.

Reflection Questions

Write your own answer first — the blurred text is one possible answer, not the only correct one.

1. Before this lab, would you have described a paused function as "fully stopped," or more like "still kind of running in the background"?

"Kind of still running" is a common intuition, especially coming from UI frameworks where things feel like they update live. The lab's model is stricter: a paused context does nothing at all until it's back on top of the stack — no partial progress, no background activity, just a held record waiting its turn.

2. Where have you already relied on call-stack behavior without naming it — a debugger's "stack trace" view, for instance?

A stack trace in an error message or debugger is a direct printout of the call stack at the moment something went wrong — each line is one context, ordered from the innermost (where the error happened) down to whatever originally kicked things off. That's the same stack this lab traced by hand, just captured automatically on a crash.

What Breaks If This Understanding Is Wrong?

If function calls feel like they happen "kind of in parallel" or "whenever they get around to it," nothing about hoisting, scope, closures, or the event loop later in this curriculum will make sense — all of them depend on "exactly one thing runs at a time, in a strict add/remove order."

The call stack (a general programming concept) and the execution context (JavaScript's own record built for every call) — the foundation the rest of this curriculum builds on.
