Functions Lab 11

Functions Are Objects

A function isn't a special kind of thing that lives outside the value system. It's a value — an object you can name, store, pass around, return, and even attach properties to — that happens to be callable.

What this lab produces: no files, no commit — a pure concept lab. You'll run short snippets in a console or with node.
Concept type: Common Concept, JavaScript-Specific Rules
ƒ
FUNCTIONS & ABSTRACTION 4 of 10

Every language needs a way to package computation so it can be reused. Languages differ on whether that package is a second-class construct or an ordinary value. JavaScript's answer: a function is just another object.

Mental Models

Mental Model 1 of 5An Object With One Extra Ability

A function value has properties like any other object — plus a hidden internal slot holding the code to run when you put () after it. Take away the callable part and what's left behaves like an ordinary object.

Mental Model 2 of 5Names Point at Functions; They Aren't the Function

Writing function greet() {} creates a function object and binds the name greet to it (the binding idea from Labs 07 and 09). A second variable can point at the very same function — one object, two names.

Mental Model 3 of 5Anything You Can Do With a Value, You Can Do With a Function

Store it in a variable, put it in an array, hand it to another function, return it from one. Languages that allow all of that are said to have first-class functions. JavaScript does — which is why callbacks (Lab 16) and closures (Lab 14) are even possible.

Mental Model 4 of 5An Analogy: The Recipe Card vs. Cooking

A recipe card is a thing: you can file it, copy it, hand it to a friend, write notes on its back. Nothing is cooked until someone follows it. greet is the card; greet() is following it. Mixing those two up is the most common mistake in this lab.

Mental Model 5 of 5Misconception: "greet" and "greet()" Mean the Same Thing

Without parentheses you're holding the function itself. With them you've run it and are holding whatever it returned. Pass the wrong one to something expecting a function and the program fails — or worse, runs code at the wrong time.

The Concept

What "a function is an object" actually means

An object (Lab 03) is a collection of named slots — properties — each holding a value. A function is exactly that, with one addition: the engine gives it an internal, hidden ability to be called, meaning to have its body run when you write () after it. You can't see that ability as a property; it's part of how the engine represents the value. Everything else about functions-as-objects follows from this one fact. 

function greet(name, punctuation) {
  return "Hello, " + name + punctuation;
}

console.log(typeof greet);           // "function"
console.log(greet instanceof Object); // true

instanceof Object asks "is this value an object, in the prototype sense?" (the full story is Lab 25 onward). For now: true means a function is not a separate species — it's an object that happens to be callable. typeof reports "function" purely as a convenience label, as Lab 03 noted.

Built-in properties: name and length

Every function arrives with a couple of properties already attached. name is the function's name as a string — "greet" for the function above. length is the number of parameters it declares — 2 for greet(name, punctuation). Note what length is not: it isn't how many arguments a given call passes (you can call greet("Ada") with one), and it isn't the size of the body.

Two precision notes. A parameter with a default value, and every parameter after it, isn't counted in length, and neither is a rest parameter — Lab 17 covers those forms. And name and length are real own properties but non-enumerable (they won't show up in Object.keys), which is why you'll see in the lab that only properties you add yourself get listed.

You can add your own properties

Because it's an object, a function accepts new properties with ordinary assignment: greet.timesCalled = 0;. Code inside the function can read and change it by referring to the function by name: greet.timesCalled++. This gives a function a small piece of memory that outlives any single call — a function's local variables vanish when each call finishes (Lab 05), but a property on the function object itself stays.

This is occasionally useful (counters, caches, flags), but it's also easy to overuse. Lab 14 introduces a cleaner, more private way to keep state with a function. The point here is to prove the claim, not to recommend the habit.

First-class functions: a function is just a value

Since a function is an object, and objects are values, a function can go anywhere a value can. Four things, concretely:

  1. Assign it to another variable: var other = greet; — now two names point at one function.
  2. Store it in a data structure: var tools = [greet, shout]; or { hello: greet }, then call tools[0]("Ada", "!").
  3. Pass it as an argument: callTwice(greet) — the receiving function gets the function itself and can call it.
  4. Return it from a function: a function can build and hand back another function.

Languages that allow all four are said to have first-class functions ("first-class" meaning: not treated as a lesser kind of thing than numbers or strings). Almost everything in the next several labs — callbacks, closures, currying — depends on this single property.

Cross-language note

Common concept: first-class functions — treating behavior as a value.

Python: also has first-class functions; a function is an object with attributes like __name__, and you can attach your own, much as here.

C#: methods aren't values by themselves; you wrap one in a delegate (or use Func<>/Action<>) to pass it around. JavaScript needs no wrapper.

JavaScript: the function is the value, with no wrapper step.

The two-character difference: greet vs greet()

A name on its own, like greet, evaluates to the function object — the recipe card from the fourth mental model. Adding () is the call operator: it runs the function and the whole expression evaluates to the return value. So callTwice(greet) hands over the function, whereas callTwice(greet("Ada", "!")) runs greet immediately and hands over its result — a string, not something callable. If the receiver then tries to call it, you get a TypeError ("... is not a function") — the error Lab 04 previewed as the cousin of ReferenceError.

Where the engine puts all this: the function object lives in memory like any object, and the name greet is a binding in the surrounding scope that points to it (Labs 07 and 09). Calling it pushes a fresh execution context on the call stack (Lab 05). The object and its call are separate things — one persists, the other lasts only as long as the call.

Reflection Questions

Write your own answer first — the blurred text is one possible answer, not the only correct one.

Reflection 1 of 3. In your own words, what is the difference between a function and calling a function? Try an analogy of your own rather than the recipe card.

The function is a stored, reusable piece of behavior you can hold, hand over or label — like a light switch installed on a wall. Calling it is flipping the switch, which makes something actually happen once. You can talk about, move, or replace the switch without ever flipping it.

Reflection 2 of 3. If you've used Python or C#, how does treating a function as a plain value compare with how that language handles it? What does JavaScript save you from writing?

Python is similar — functions are objects there too. In C#, you typically wrap a method in a delegate or Func<> before you can pass it around; JavaScript skips that step because the function already is a value. The trade-off is that mistakes like passing greet() instead of greet are easy to make and only show up when the program runs.

Reflection 3 of 3. You can keep a counter in a function's own property. Based on Lab 05's model of execution contexts, why is that different from keeping the counter in a var inside the function? And what might be unappealing about putting state on the function object?

A local var belongs to one call's execution context and is discarded when that call finishes, so it restarts at its initial value every time. A property belongs to the function object, which persists, so it accumulates. The downside is that the property is public: any code that can see greet can read or overwrite greet.timesCalled. Lab 14 (closures) shows how to keep persistent state private.

What Breaks If This Understanding Is Wrong?

If functions feel like a separate category from values, callbacks (Lab 16) will look like magic — "why can I hand over code?" — and closures (Lab 14) will be unexplainable, since a closure is a function value carried out of the scope where it was made. Method calls and this (Lab 18) also rest on this: a method is just a function stored in an object's property.

What JavaScript Concept Was Learned Today?

A function in JavaScript is an object that can also be called: it has properties (including built-in name and length, and any you add), and it's a plain value that can be assigned, stored, passed and returned. The name greet refers to the function; greet() runs it.

Relates to: ƒ Functions & Abstraction (4 of 10) — how do we package, pass around, and reuse computation? JavaScript's answer: make the package an ordinary value, with no special wrapper.
