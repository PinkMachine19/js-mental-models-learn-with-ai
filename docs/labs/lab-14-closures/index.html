Functions Lab 14

Closures

A function that remembers the scope it was created in — even after the function that created it has finished. The idea that makes callbacks, private state and half of everyday JavaScript work.

What this lab produces: no files, no commit — a pure concept lab. You'll run short snippets in a console or with node.
Concept type: Common Concept, JavaScript-Specific Rules
ƒ
FUNCTIONS & ABSTRACTION 4 of 10
◎
NAMES & SCOPE 2 of 10

Once functions are values that can leave the place they were made (Lab 11), a language must decide what names they can still see. JavaScript's answer: the scope where the function was defined comes along with it, for as long as the function lives.

Mental Models

Mental Model 1 of 5A Function Carries Its Defining Scope

Every function, at the moment it's created, remembers the scope it was created in (the lexical environment link from Lab 09). Wherever the function travels afterward, that link goes with it. That function-plus-link combination is what's called a closure.

Mental Model 2 of 5Returning Ends the Call, Not the Variables

When makeCounter() returns, its execution context is popped off the call stack (Lab 05). But the environment holding count isn't thrown away, because the returned function still points to it. Memory is only reclaimed once nothing reachable refers to it.

Mental Model 3 of 5One Call, One Fresh Scope

Each call to makeCounter() creates a brand-new environment with its own count. The functions it hands back each point at their own, so two counters never interfere with each other.

Mental Model 4 of 5An Analogy: The Function Holds a Key

The variables live in a locker. The returned function carries the only key. Outside code can see the function but not the locker's contents. And the locker stays in the building for as long as anyone still holds a key.

Mental Model 5 of 5Misconception: "It Remembers the Value It Saw"

A closure holds on to the variable, not a snapshot of its value. If the variable changes later, the function sees the new value. That one fact explains the classic loop bug later in this lab.

The Concept

The puzzle

Lab 05 told us that when a function returns, its execution context is popped off the call stack and it's gone. Lab 09 told us each function has a link to the scope where it was defined. Put those together and a question appears: 

function makeCounter() {
  var count = 0;
  return function () {
    count++;
    return count;
  };
}

var a = makeCounter();   // makeCounter has finished and returned...
a();                     // ...so how can this still see count?

The answer is that the context was popped, but the variables weren't discarded.

What a closure is

A closure is a function together with a reference to the lexical environment (Lab 09) it was created in. "Lexical" means decided by where the code is written, not by who calls it. The function was written inside makeCounter, so wherever it later goes — returned, stored, passed as an argument — it can still look up count through that link.

Technically every function in JavaScript is a closure; there's no special syntax to "make" one. People use the word for the interesting case: a function that is used outside the scope where it was made, which is exactly when the remembered scope matters.

What the engine is doing

  1. Calling makeCounter() creates an execution context (Lab 05) and a new environment holding count = 0.
  2. The inner function is created. As with every function, it stores a hidden link to the environment current at that moment.
  3. The inner function is returned. The call finishes and the execution context is popped.
  4. The environment is not thrown away, because the returned function still refers to it. Memory is reclaimed only when nothing reachable refers to something — called garbage collection, revisited in Lab 38.
  5. Each later call a() creates its own short-lived context for the inner function, whose scope chain (Lab 09) leads out to that surviving environment and finds count.

Because step 1 happens on every call, var b = makeCounter(); makes a different environment with a different count. That's what makes private, per-instance state possible with no classes at all: nothing outside can reach count except through the function that holds the key.

Variables are captured, not values

The closure refers to the variable itself. If the variable changes after the function was created, the function sees the change: 

function makeReader() {
  var x = 1;
  function get() { return x; }
  x = 2;                 // changed AFTER get was created
  return get;
}

makeReader()();          // 2, not 1
Cross-language note

Common concept: closures — functions capturing variables from enclosing scopes.

Python: has closures too, but an inner function that wants to reassign an outer variable must declare it nonlocal; otherwise assignment makes a new local.

C#: lambdas capture variables (not values), with the same "single shared loop variable" trap in a for loop.

JavaScript: assignment to a captured variable just works — no declaration needed — because the scope chain is searched for the existing binding.

The classic loop trap — and why let fixes it

var fns = [];
for (var i = 0; i < 3; i++) {
  fns.push(function () { return i; });
}
fns[0]();   // 3
fns[1]();   // 3
fns[2]();   // 3

var i is function-scoped (Lab 07): there's one i for the entire loop, and all three functions hold the same variable. By the time they're called, the loop has finished and left it at 3. Change var to let and the results become 0, 1, 2: a let in a loop header gets a fresh binding for each iteration, so each function captures its own. Before let, the fix was an IIFE (Lab 13) that took i as a parameter, creating a new scope per iteration.

Cost: a captured environment stays in memory as long as any function referring to it does. That's usually exactly what you want, but a long-lived function that captures a large value keeps that value alive too.

Reflection Questions

Write your own answer first — the blurred text is one possible answer, not the only correct one.

Reflection 1 of 3. Explain closures to someone who knows functions but has never heard the word, using an analogy of your own (not the key and locker).

A closure is a function that remembers where it was born. Imagine a traveller who leaves home with a bag containing items from the house they grew up in: wherever they go, they can still reach into the bag, and nobody else can. The function is the traveller; the scope it was created in is the bag.

Reflection 2 of 3. In your own words, why does a var loop give 3, 3, 3 while a let loop gives 0, 1, 2?

With var there is one variable i shared by every iteration, and all three functions point at it, so they all see its final value after the loop. With let each iteration gets its own fresh i, so each function closes over a different variable that never changes again.

Reflection 3 of 3. A closure keeps a captured value alive for as long as the function exists. Give one situation where that is exactly what you want, and one where it might be a problem.

Wanted: private state, such as a counter or a cache that must persist between calls. Problem: a long-lived function that only needs one small value but captures a scope containing a very large array or object, keeping that memory from ever being reclaimed. (Engines can avoid retaining variables that no function uses, but a variable that is captured stays alive as long as the function does.)

What Breaks If This Understanding Is Wrong?

Callbacks (Lab 16), event handlers, timers and promises all rely on a function running later and still seeing the variables around where it was written — if you think those variables vanish when the outer function returns, every async example in the course will look broken. Lab 15 (factories, currying, memoization) is closures applied directly, and the later this labs depend on knowing which things are looked up through scope (variables) and which are not.

What JavaScript Concept Was Learned Today?

A closure is a function plus the scope it was created in. When an outer call finishes its execution context goes away, but any environment still referred to by a surviving function is kept alive, giving that function private, persistent state. Closures hold variables, not copies — which is why a var loop produces shared state and a let loop doesn't.

Relates to: ƒ Functions & Abstraction (4 of 10) + ◎ Names & Scope (2 of 10) — functions that travel need a rule for which names they can still see; JavaScript's is "the scope where you were defined."
