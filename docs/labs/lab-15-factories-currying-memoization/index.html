Closures in Practice: Factories, Currying & Memoization

Three famous-sounding patterns, one underlying mechanism. Build each from nothing, and closures stop being an abstract rule and become a toolkit.

FUNCTIONS & ABSTRACTION 4 of 10

Once a function can carry private state with it (Lab 14), you can use it to build other functions, feed arguments in over time, and remember earlier answers. This lab shows JavaScript's everyday idioms for each.

Mental Models

Mental Model 1 of 5A Factory Builds Functions to Order

A factory is a function whose job is to build and return another function (or object), customized by the arguments it was called with. The customization lives in a closure, so each product remembers its own settings.

Mental Model 2 of 5Currying: One Argument Per Call

A curried function takes one argument and returns a function waiting for the next. Each stage remembers the arguments before it in its closure, so add(2)(3) works, and add(2) alone is a useful, reusable function.

Mental Model 3 of 5Memoization: Look It Up Before You Compute It

A memoized function stores each result in a private cache the first time it computes it. The next call with the same input finds the answer in the cache and skips the work entirely. The cache is just a captured variable.

Mental Model 4 of 5An Analogy: Presets, Forms and Sticky Notes

A factory is a machine with a preset button ("large oat latte") built to your settings. Currying is a long form you fill in across several visits, saving what you've entered so far. Memoization is the sticky note you leave on the fridge so you don't redo the sum next time.

Mental Model 5 of 5Misconception: "These Need Special Language Support"

There's no curry keyword or memoize feature in JavaScript. Each pattern is an ordinary function that returns a function, relying only on the closures from Lab 14. Seeing that is what stops them from feeling like magic.

The Concept

One mechanism, three habits

Lab 14 established the mechanism: a function remembers the scope it was created in, so variables from a finished call can live on, private, inside a returned function. This lab is about three recurring ways to use that. None of them needs special syntax — each is a function that returns a function.

Factories: functions that build functions

A factory is a function whose job is to create and return something customized — most often another function, sometimes an object: 

function makeMultiplier(factor) {
  return function (n) {
    return n * factor;
  };
}

var twice  = makeMultiplier(2);
var thrice = makeMultiplier(3);
twice(5);    // 10
thrice(5);   // 15

factor is a parameter of makeMultiplier; after the call finishes, it lives on inside each returned function's closure. A factory can also return several functions that share one private variable: 

function makeAccount(start) {
  var balance = start;
  return {
    deposit: function (n) { balance += n; return balance; },
    read:    function ()  { return balance; }
  };
}

Nothing outside can change balance except through deposit — the private-state benefit from Lab 14, now packaged as a reusable constructor of small objects. (Later labs show other ways to build objects, classes included; the factory is the lightest one.)

Currying and partial application

Currying (named after the mathematician Haskell Curry) turns a function of several arguments into a chain of functions that each take one: 

function add(a) {
  return function (b) {
    return a + b;
  };
}

add(2)(3);          // 5
var addTen = add(10);   // a new function, waiting for b
addTen(5);          // 15
addTen(20);         // 30

The inner function holds a in its closure. The payoff is addTen: calling add with just the first argument gives you a specialized, reusable function. Giving a function some of its arguments now and getting back a function that wants the rest is called partial application. The two are related but not identical: currying always works one argument per call, while partial application can fix any number at once (and Lab 19's bind does it too).

Cross-language note

Common concept: partial application — fixing some arguments ahead of time.

Python: provides it in the standard library as functools.partial; writing curried chains by hand is unusual.

JavaScript: no library needed — closures make the hand-written version a few lines, so you will see it in real code.

Memoization: remember, don't recompute

Memoization (from "memo": a note to self) wraps a function so that its results are saved, keyed by the input, and returned from the saved copy when the same input comes in again: 

function memoize(fn) {
  var cache = {};
  return function (n) {
    if (cache.hasOwnProperty(n)) { return cache[n]; }
    var result = fn(n);
    cache[n] = result;
    return result;
  };
}

cache is created once when memoize runs and is then captured by the returned function: it persists between calls, and nothing else can touch it. Three honest caveats:

  • Only for pure functions — those whose result depends only on their inputs and which do nothing else. Memoizing something that reads the clock, generates random numbers, or changes outside state returns stale answers.
  • The cache grows without limit, and holds everything it stores for as long as the function exists (memory, Lab 38). Later collections (Map, Lab 37) make cleaner caches.
  • Object keys are strings, so inputs 1 and "1" land on the same cache entry; this simple version also handles one argument only.

Where the engine is involved: in all three patterns, the same thing happens. A call creates an environment; an inner function is created with a link to it; the call returns, but the environment survives because that inner function is still reachable. Only the contents of the environment differ: a factor, an a, a cache.

Reflection Questions

Write your own answer first — the blurred text is one possible answer, not the only correct one.

Reflection 1 of 3. Pick one of the three patterns (factory, currying, memoization) and describe a real task from your own experience where it would fit well.

A factory suits building several similar helpers from configuration, like a makeLogger(prefix) that returns a function adding a prefix to messages. Currying suits reusing a general function with its first argument fixed, such as a discount(rate) function applied to many prices. Memoization suits a slow, repeated pure calculation like looking up the same lookup table value or computing a recursive result such as Fibonacci.

Reflection 2 of 3. Explain, in your own words, why memoizing the nextLabel function from the lab gave a wrong second answer. What property must a function have to be safely memoized?

The cached answer was reused without running the function, so the counter outside it didn't advance, and the answer no longer matched what the function would return. A function must be pure: given the same input it always returns the same output, and it has no other effects that someone relies on happening each call.

Reflection 3 of 3. The memoizer's cache never shrinks. If this function runs for hours with millions of different inputs, what could go wrong, and what is one way you could limit it?

The cache keeps every result alive for as long as the memoized function exists, so memory use can grow without bound. You could limit it by capping the number of stored entries (discarding the oldest), clearing it periodically, or using a collection built for this such as Map (Lab 37) or, for object keys that should be reclaimable, WeakMap (Lab 38).

What Breaks If This Understanding Is Wrong?

Without seeing these as ordinary closures, patterns in real codebases — configured helper functions, handlers with preset arguments, cached lookups — look like unrelated tricks. Callbacks (Lab 16) often arrive as factory-built functions, bind (Lab 19) is partial application under another name, and the later cache-related labs (Map, WeakMap) assume you've already seen why a cache is worth building.

What JavaScript Concept Was Learned Today?

Factories, currying and memoization are not separate language features but three habits built on closures: a function that returns a customized function, a function that takes its arguments over several calls, and a function that keeps a private cache of earlier results. Each works because the returned function keeps the scope where it was created alive.
