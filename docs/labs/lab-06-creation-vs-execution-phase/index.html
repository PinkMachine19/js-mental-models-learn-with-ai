Creation Phase vs Execution Phase

Lab 05 showed a context gets pushed and popped. Now we open one up: it's actually built in two separate passes, and that's what makes "hoisting" look the way it does.

Hoisting sits at the intersection of how code executes and where names become visible.

Mental Models

Two Passes, Same Code

Nothing runs during the first pass — it only registers what exists. The second pass is the one that actually executes line by line.

Registered Empty vs Registered Full

Both get a slot in pass 1, but a var starts empty while a function declaration starts already holding the whole function.

Hoisting Is Not Teleportation

The lines of your file never move. Only the registration step happens before execution reaches them — it just looks like the declaration "moved up."

The Concept

Building an execution context is a two-step process

When the engine builds an execution context (Lab 05), it doesn't immediately start running your code top to bottom. It first does a full pass over that context called the creation phase, registering every var and function declaration it finds — before a single line has actually executed. Only after that's done does the execution phase begin, running your code top to bottom for real.

What gets registered, and how

  1. Every var name is registered and set to undefined — a slot exists, but empty.
  2. Every function declaration is registered with its entire function already as the value — fully ready to call.
  3. The execution phase then runs top to bottom, assigning real values to vars as their lines are reached.

This two-phase process is what people call "hoisting" — but nothing physically moves, as the third mental-model diagram above shows. The registration was always going to happen first; it only looks like the declaration relocated.

Reflection Questions

Write your own answer first — the blurred text is one possible answer, not the only correct one.

1. Even though calling a function declaration before its line "works," why might relying on that be a risky habit?

It works for a plain function declaration today, but the exact same-looking code breaks silently (or throws) the moment someone refactors it into a function expression, an arrow function, or moves it into a conditional block. Reading code top to bottom, in the order it actually runs, avoids depending on a subtlety that's easy to break by accident.

2. How does the two-phase model explain why declaring the same var name twice in one scope doesn't cause an error?

The creation phase only registers a name once per scope, regardless of how many times var mentions it — so a second var statement for the same name isn't creating a new binding, it's just another assignment to the one that already exists.

What Breaks If This Understanding Is Wrong?

Without the two-phase model, the Temporal Dead Zone (Lab 07) looks like an arbitrary rule instead of a direct consequence of it — let/const go through the same creation phase, just registered in a different, inaccessible state.

What JavaScript Concept Was Learned Today?

Every execution context is built in two passes — a creation phase that registers names first, then an execution phase that actually runs the code — and that's the real mechanism behind what's casually called "hoisting."
