var, let, const & the Temporal Dead Zone

let and const go through the same two-phase registration as var — they just come out the other side in a very different, much stricter state.

Every language needs rules for where a name is visible. JavaScript has three different declaration forms with three different answers.

Mental Models

Registered Open vs Registered Locked

Both get a slot in the creation phase. var's slot is immediately readable; let/const's slot is locked until its own declaration line runs.

The TDZ Is a Span of Time

From the start of the block until its own declaration line executes, a let/const name exists but touching it throws.

Block Scope vs Function Scope

let/const stay contained to the block they're declared in. var ignores block boundaries and belongs to the whole enclosing function (or the global scope).

The Concept

Block-scoped variables aren't a JavaScript invention — the TDZ is

Most languages have some notion of a variable being scoped to a smaller block than a whole function. What's specific to JavaScript is the Temporal Dead Zone: a deliberately strict, loud-failure zone that let/const sit in between being registered and being declared.

Cross-language note

Common concept: variables scoped to a block.

Python: has no block scope at all — a variable assigned inside an if or for is visible in the whole enclosing function afterward, closer to how var behaves than how let does.

JavaScript: let/const are genuinely trapped inside the block (third diagram above) — a behavior Python simply doesn't have an equivalent for.

Same creation phase, different starting state

Building on Lab 06: let and const are registered during the creation phase too — the name exists from the very start of its block. But instead of starting as undefined like var, it starts uninitialized, in the Temporal Dead Zone. Touching it before its own declaration line runs throws ReferenceError: Cannot access '...' before initialization — a deliberately loud failure instead of a silent undefined.

Scope: function-wide vs block-contained

The second difference is scope shape. var belongs to the nearest enclosing function (or the global scope if there is none) — it ignores if/for/ other block boundaries entirely. let and const are genuinely block-scoped: they exist only inside the { } they were declared in.

Reflection Questions

Write your own answer first — the blurred text is one possible answer, not the only correct one.

1. Given what you now know, why might modern style guides recommend const by default, let only when reassignment is needed, and var essentially never?

const/let give you block scope (fewer accidental leaks past an if or for) and a loud TDZ error instead of a silent undefined when something's used too early. var's looser rules made sense before block scope existed, but now mostly just remove safety nets without adding any capability let/const lack.

2. Would you rather debug a silent undefined from var, or a loud TDZ error from let? Why?

Most developers prefer the loud error — it points directly at the exact line and reason, versus an undefined that might not cause a visible problem until much later in the program, far from where the actual mistake was made.

What Breaks If This Understanding Is Wrong?

The scope chain (Lab 09) and closures (Lab 14) both depend on knowing exactly which block a variable belongs to — mixing up var's function-wide scope with let/const's block scope will make both of those labs' predictions consistently wrong in loops and conditionals.

What JavaScript Concept Was Learned Today?

let and const go through the same creation-phase registration as var, but land in a locked, block-scoped state (the Temporal Dead Zone) instead of an open, function-scoped undefined.
